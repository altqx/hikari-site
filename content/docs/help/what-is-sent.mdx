HikariSub sends **anonymous usage data**: which features are used, errors and crashes, and how fast things open. It shows what people use, what goes wrong and what is slow, so work can go where it helps. It never sends your files, their names or what is in them.

It is **on by default**, also in a copy updated from an earlier version and after importing legacy settings, which never had this option. This page lists every event and every property HikariSub can send, and how to turn it off.

This page is about the HikariSub app. This website uses Cloudflare Web Analytics instead, with no cookies.

[Discord presence](#discord-presence), which shows what you are doing in your Discord status, is separate from usage data and off by default.

## Turning it off

Any of these turns it off:

- **File › Settings › Updates and privacy › Privacy › Send anonymous usage data**. The change applies on **OK** or **Apply**.
- **Send anonymous usage data** on the Updates and privacy step of the [Getting started window](/en/docs/get-started/getting-started-window#updates-and-privacy). It is saved when you press **Finish**.
- The `DO_NOT_TRACK` environment variable, set to anything but `0`, turns it off for each run that has it. On Linux, start HikariSub with `DO_NOT_TRACK=1 hikarisub`, or export it in your shell profile. On Windows, add a user environment variable named `DO_NOT_TRACK` with the value `1`. The switch in Settings still shows your setting.

Both switches are the same setting, and both have a **What is sent** link that opens the full list in your browser.

Only release packages send. Every release package (setup, portable zip, AppImage, deb, rpm and tar.gz) carries the key that lets HikariSub send, so they all send while the switch is on. Builds from source don't carry it, and neither do forks' builds or test builds: they queue nothing and send nothing, though the switch still shows.

**Reset page** on the Updates and privacy page, and **Reset all settings…**, turn it back on, since on is the default.

### What turning it off does

It takes effect at once:

- Nothing more is queued or sent. A send that is under way is stopped.
- The events waiting to be sent are deleted, from memory and from the cache folder.
- The [anonymous ID](#the-anonymous-id) is deleted.

Events that were already sent are not deleted. [Crash and freeze reports](#crash-and-freeze-reports) are not affected: they go only when you send them, or when **Always send crash reports** is on.

The first send is 60 seconds after HikariSub starts. If you turn it off before then, for example on Getting started's Updates and privacy step at the first start, nothing has been sent.

With `DO_NOT_TRACK` set, the events waiting from earlier runs are deleted when HikariSub starts. The anonymous ID is kept.

If you turn it on again, HikariSub starts a new ID. The session length and the frame counts in `app_closed` then count from that moment.

## Where it goes

Events go to PostHog Cloud EU through HikariSub's own proxy, at `https://i.hikarisub.org`. The proxy runs on Cloudflare and only forwards the events to PostHog. It keeps no logs, and it doesn't pass your IP address on, so PostHog sees the proxy's address instead of yours. There is no fallback: if the proxy can't be reached, nothing goes to PostHog's own address, and the events wait for the next send.

0.1.0-beta.3 and earlier send straight to `https://eu.i.posthog.com`. PostHog then receives your IP address with each send, as any server does, and the HikariSub project there discards it.

- Every event asks PostHog to make no location lookup from the IP address (`$geoip_disable`) and no person profile (`$process_person_profile`).
- Each send also carries HikariSub's project key, which is the same in every copy, and the user agent `HikariSub/` followed by the version.

## The anonymous ID

Events go under a random ID (a UUID), made the first time HikariSub queues an event. It is not made from anything about you or your computer, and is not tied to anything else.

It is kept in `state.json` in your [user folder](/en/docs/automation/user-folder#settings-files), as `usageDataId` under `privacy`.

To get a new one, turn **Send anonymous usage data** off, press **Apply**, then turn it on again. **Reset all settings…** also clears it.

Each run of HikariSub also has a session ID, a new random UUID for every start. It is not kept in your settings.

## When it is sent

- Events wait in memory and in `analytics-queue.json` in the cache folder: `%LOCALAPPDATA%\HikariSub\cache` on Windows, `~/.cache/hikarisub` on Linux. Portable copies use it too.
- The queue holds at most 1000 events, or 1 MB of them. Past that, the oldest are dropped.
- HikariSub sends up to 100 events at a time: 60 seconds after it starts, then every 5 minutes.
- At quit, after the window has closed, it sends once more and waits at most 2 seconds for it.
- HikariSub never waits for a send, and a failed send shows no message. Without a connection, the events wait for the next send, also in a later run.
- If PostHog refuses a batch outright, those events are dropped and not tried again.
- When HikariSub reads the queue at the next start, it checks each event against the lists below again and drops any that doesn't match.

## What is never sent

- File names and paths, of subtitles, video, audio, scripts or anything else
- Subtitle text, script text, or anything else you typed
- Style names and font names
- The names of scripts, other than the scripts that come with HikariSub
- The names of your saved layouts
- Which values you chose in Getting started
- An automation macro's shortcut

Every property is an ID from a fixed list, a bucket, a yes or no, a version or a count. Before an event is queued, HikariSub checks it against the lists below, and drops any event that doesn't match them.

## Every event

### On every event

| Property | Value |
| --- | --- |
| `distinct_id` | The [anonymous ID](#the-anonymous-id) |
| `$process_person_profile` | `false`: PostHog makes no person profile |
| `$geoip_disable` | `true`: PostHog makes no location lookup |
| `$session_id` | This run's random session ID |
| `$lib` | `hikarisub` |
| `$lib_version` | The app version, such as `0.1.0-beta.1` |

Each event also has its name and the time it happened, in UTC, to the second.

### Start and quit

| Event | Sent | Properties |
| --- | --- | --- |
| `app_started` | When the main window first shows | See below |
| `app_closed` | At quit | `session_length` and the frame counts, below |

`app_started` has:

| Property | Value |
| --- | --- |
| `version` | The app version |
| `channel` | `stable` or `prerelease` |
| `$os` | `windows`, `linux` or `other` |
| `$os_version` | The system's version as Qt reports it, such as `11` or `24.04`; `other` if it is longer than 24 characters or has other characters than letters, digits, `.`, `_` and `-` |
| `arch` | `x86_64`, `arm64` or `other` |
| `package` | `installer`, `portable`, `appimage`, `deb`, `rpm`, `aur` (when the AUR packages are out) or `build_tree` |
| `qt_version` | The Qt version, such as `6.11.2` |
| `language` | The interface language: `en`, `ko_KR`, `pl`, `ta` or `th_TH` |
| `theme` | `light`, `dark`, `high_contrast_white` or `high_contrast_black` |
| `theme_follows_system` | `true` or `false` |
| `layout` | The layout the window opened in: `editing`, `timing`, `translation`, `typesetting`, `karaoke`, `saved` (one of your saved layouts, not its name) or `custom` |
| `screens` | `1`, `2` or `3+` |
| `scale` | The window's display scale: `1x`, `1.25x`, `1.5x`, `2x` or `3x+` |
| `startup_time` | How long the window took to show, as a time bucket |

`app_closed` has:

| Property | Value |
| --- | --- |
| `session_length` | `<1m`, `1-5m`, `5-15m`, `15-60m`, `1-3h` or `3h+`, since the start or since you turned sending on |
| `render_frames_lt8ms`, `render_frames_8_16ms`, `render_frames_16_33ms`, `render_frames_33_66ms`, `render_frames_66_200ms`, `render_frames_200ms_plus` | How many frames of subtitles took that long to draw in this run, while sending was on: under 8 ms, 8 to 16 ms, and so on, up to 200 ms or more |

The time buckets, used by `startup_time` and `open_time`, are `<250ms`, `250-500ms`, `0.5-1s`, `1-2s`, `2-5s`, `5-15s`, `15-60s` and `60s+`.

### Features used

| Event | Sent | Properties |
| --- | --- | --- |
| `command_used` | When a command runs | `command`, `via` |
| `panel_opened` | When you show a panel, from the View menu, a panel's menu or a button | `panel` |
| `dialog_opened` | When a dialog or window opens | `dialog` |
| `layout_changed` | When you choose a layout | `layout` |
| `getting_started_finished` | When you press **Finish** in Getting started | `pages_changed` |
| `getting_started_skipped` | When you close Getting started without finishing: **Skip setup**, <kbd>Esc</kbd> or closing the window | None |
| `star_prompt_shown` | When the [suggestion to star HikariSub on GitHub](#star-on-github-suggestion) shows, at most twice ever | None |
| `star_prompt_clicked` | When you press its **Star on GitHub** | None |

- `command`: the command's ID in the shortcut list, such as `GLOBAL_SAVE_SUBS` or `AUDIO_PLAY`. Only the commands in that list are sent. Automation macros are never sent.
- `via`: `key` for a command a key ran, or `pointer` for one from a menu, a toolbar or a panel's button.
- `panel`: `video`, `audio`, `editor`, `grid`, `reference`, `timing`, `search`, `automation`, `original`, `log`, `styles`, `template` or `spellchecker`.
- `dialog`: `about`, `alignToVideo`, `allTagsEdition`, `aspectRatio`, `autosaves`, `columns`, `crashReport`, `credits`, `dummyVideo`, `extendTracking`, `fontCatalogClashes`, `fontCatalogs`, `fontCollector`, `fontPicker`, `fontsFromSubtitles`, `gettingStarted`, `history`, `hotkeyCapture`, `kanjiTimer`, `karaokeCheck`, `listChooser`, `manageLayouts`, `motionData`, `movePanel`, `perspectiveTracking`, `reportIssue`, `resample`, `saveLayout`, `scriptInfoOnSave`, `scriptProperties`, `selectLines`, `setNewFps`, `settings`, `settingsImport`, `shapesEdition`, `spellAddedWords`, `styleClashes`, `styleManager`, `translationShift`, `unsavedChanges`, `updateAvailable`, `videoDetails` or `whatsNew`. A script's dialog is `automation_script`, whichever script it is.
- `layout`: `editing`, `timing`, `translation`, `typesetting`, `karaoke`, or `saved` for one of your saved layouts. Its name is not sent.
- `pages_changed`: the Getting started pages whose settings **Finish** changed, from `language`, `import`, `look`, `layout`, `media`, `editing`, `updates` and `files`. Which values you chose is not sent. If you turn sending off on the Updates and privacy step, this event is not sent either.

How often:

- `command_used` is sent once per command and `via` in each run.
- `panel_opened` and `dialog_opened` are sent once per panel or dialog in each run.
- `layout_changed` is sent each time, up to 20 times in each run.

### Errors and crashes

| Event | Sent | Properties |
| --- | --- | --- |
| `automation_error` | When a macro fails, its script's process is lost or force-stopped, or a script doesn't load | `kind`, `script` |
| `$exception` | At the start after HikariSub crashed or was closed while frozen, and when it comes back from a freeze | `$exception_list`, `$debug_images`, `$exception_level`, `crashed_version`, `report_id`, `freeze_seconds` |

- `kind`: `failed`, `lost`, `stopped` or `load_failed`.
- `script`: the file name of a script that comes with HikariSub, such as `strip-tags.lua`, with spaces turned into `_` (`skew_gradient.lua`). It counts as one only while its contents match the copy HikariSub came with, in the program's folder or copied to your user folder. Any other script is `user script`, and its name is not sent. A macro whose check declines to run on your selection is not an error and sends nothing.
- `$exception_list`: one entry with the crash's type, how it was caught, and where it happened:
  - the type: on Linux the signal, `SIGSEGV`, `SIGABRT`, `SIGBUS`, `SIGFPE` or `SIGILL`; on Windows the exception's name, such as `EXCEPTION_ACCESS_VIOLATION`, or else its code, `0x…`; `APP_HANG` for a freeze;
  - how it was caught: `signal`, `seh` or, for a freeze, `watchdog`; not handled;
  - up to 32 stack frames, each a module and an offset. The module is a file name only, and only for HikariSub's own files and the system's (in `/usr` or `/lib`, or the Windows folder). Any other module is `other`. The offset is a hex number into that module.
  - from 0.1.0-beta.2, a frame in a named module also has `image_addr`, the address the module was loaded at, and `instruction_addr`, that address plus the offset. An `other` module has neither.
- `$debug_images` (from 0.1.0-beta.2): for each named module, its file name (`code_file`, the same as the frame's module), where it was loaded (`image_addr`) and its debug id: the GNU build-id on Linux, or the GUID and age of its PDB on Windows. The debug id says which build the module is, so PostHog can show function names and lines from the symbols each release uploads. It names the build, not your computer.
- `$exception_level`: `fatal`, or `error` for a freeze HikariSub came back from.
- `crashed_version`: the version that crashed or froze.
- `report_id`: a random UUID made for the report, the same as its [`crash_report`](#crash-and-freeze-reports)'s.
- `freeze_seconds`: for a freeze, how many seconds the window didn't respond.

### Opening video and audio

| Event | Sent | Properties |
| --- | --- | --- |
| `video_opened` | When opening a video ends | `open_time`, `outcome`, `kind` |
| `audio_opened` | When opening audio ends: it is all loaded, or it failed | `open_time`, `outcome`, `kind` |

- `open_time`: how long it took, as a time bucket.
- `outcome`: `ready` or `failed`.
- `kind`: `file` or `dummy` for video; `file`, `from_video` or `dummy` for audio.

Audio that you close or replace before it finishes loading sends nothing.

## Crash and freeze reports

When HikariSub crashes, or its window doesn't answer for 10 seconds, it writes a small record to the cache folder: the version, the type of crash or how long it froze, and the stack frames, as above. It does so whether usage data is on or off. The record is not a crash dump: it holds no memory, no file names and no text. At the next start, or when HikariSub comes back from a freeze, the record becomes a report and HikariSub asks you about it: see [Crash and freeze reports](/en/docs/help/reporting-problems#crash-and-freeze-reports).

A report goes once, only when you press **Send report** in its window, or by itself when you have turned on **Always send crash reports**. That is so even with usage data off.

- **With usage data on**, the record alone was already queued as `$exception`, like any other event. **Send report** then sends only `crash_report`, which holds the rest: your note, the Log lines and the settings summary. `report_id` links the two. If you turned usage data off after the record was queued, the queue was deleted, so **Send report** sends the record again.
- **With usage data off, or `DO_NOT_TRACK` set**, **Send report** sends both `$exception` and `crash_report`, under a random ID made for that one report and kept nowhere. No [anonymous ID](#the-anonymous-id) is made, and there is no session ID.

A report goes straight away to the same address, through the same proxy, with the same project key and user agent, and is not queued. Only release packages can send one.

`crash_report` has:

| Property | Value |
| --- | --- |
| `report_id` | The same random UUID as its `$exception`'s |
| `kind` | `crash` or `freeze` |
| `note` | What you typed in the report window, up to 4,000 characters. Left out when you typed nothing |
| `log` | The Log's last 200 lines, with file names, quoted text, font names and folders replaced |
| `settings` | The settings summary: ids and plain values from a fixed list, never a folder, font or name |
| `version`, `channel`, `$os`, `$os_version`, `arch`, `package`, `qt_version` | As in `app_started` |

[What a report holds](/en/docs/help/reporting-problems#what-a-report-holds) lists the settings in the summary and how the Log lines are changed. HikariSub still offers your last session after a crash; see [After a crash](/en/docs/help/troubleshooting#after-a-crash).

## Discord presence

HikariSub can show what you are doing in your Discord status. It is **off by default**. Turn it on in **File › Settings › Updates and privacy › Privacy › Show what I am doing in Discord**.

It talks only to the Discord app on the same computer, never to a HikariSub server. Discord shows the status to the people who can see yours. Without Discord running, nothing happens; HikariSub looks for Discord again every 20 seconds.

| Shown | Value |
| --- | --- |
| Activity | "Editing subtitles" |
| Mode | Editing, Timing, Translation, Typesetting or Karaoke: the workspace layout you chose last |
| Time | How long since presence was turned on in this run |
| Images | The HikariSub icon, and the mode's icon |
| Button | **Get HikariSub**, which opens [hikarisub.org](https://hikarisub.org) |

The texts are in HikariSub's interface language. **Include the file name**, under the switch and also off by default, adds the current tab's file name after the mode, such as `Timing · episode01.ass`. Only the name is sent, never its folder.

It never sends the video or audio name, folders or paths, subtitle text, line counts or progress.

Turning it off clears your status at once, and so does quitting HikariSub.

## Star on GitHub suggestion

Once you have used HikariSub for a while, a quiet message may suggest starring it on GitHub: **Enjoying HikariSub?** "A star on GitHub helps others find it." **Star on GitHub** opens [HikariSub on GitHub](https://github.com/altqx/hikari); **Not now** closes it. It never asks for anything else: no rating, sign-in or email.

It shows at most twice ever, and never again once you press **Star on GitHub**:

- only after HikariSub has been opened on at least 5 different days, with at least 3 hours in all while its window was active and a file was open, and at least 10 minutes into the current run;
- never on the first run, or on the first run after an update;
- never while video or audio plays, in full screen, while a dialog is open, or within 10 seconds of your last key press;
- at least 30 days after it last showed, however you closed it.

There is no setting to turn it off: it never shows more than twice.

The counts it needs stay in your [settings file](/en/docs/automation/user-folder#settings-files) on this computer. Nothing about it is sent, except with usage data on: [`star_prompt_shown` and `star_prompt_clicked`](#features-used), with no properties.

## AI

HikariSub sends nothing to an AI provider until you add one in **File › Settings › AI**. AI features are on at first. **Turn off all AI features** on that page turns them off: with it ticked, HikariSub reads no keys, downloads nothing and starts nothing for AI.

- **The AI component.** The first time you test or add a provider, or turn on the MCP server, HikariSub downloads its AI component from HikariSub's releases on GitHub. The provider form, or the MCP section, says how big it is before it starts.
  - **Checking:** once it is there, and while AI features are on, HikariSub checks those releases for a newer version at start and once an hour. Each check fetches one small signed file, and sends only the user agent `HikariSub-AI` and a tag saying which copy of that file it already has. It sends nothing about you, your providers or your subtitles.
  - **Updating:** a newer version downloads in the background. HikariSub switches to it when AI has been unused for two minutes, and goes back to the version before if the new one fails to start, or crashes twice within 10 minutes.
  - **Signature:** every download is checked against HikariSub's release key, as app updates are (see [Checking a download](/en/docs/get-started/install#checking-a-download)).
  - **Turning it off:** automatic updates are on by default. An administrator can turn them off for the whole computer: set the environment variable `HIKARI_AI_AUTO_UPDATE` to `0`, set `ai_auto_update` to `false` in `/etc/hikarisub/policy.json` on Linux, or set `AiAutoUpdate` to `0` under `HKLM\SOFTWARE\Policies\HikariSub` on Windows. HikariSub then still checks, but downloads nothing. **Turn off all AI features** stops the checks too.
- **Testing a provider.** **Test connection**, **Add** and **Refresh models** ask the provider for its list of models, and send your key with the request. Nothing from your subtitles is sent.
- **Signing in.** **Sign in with ChatGPT…**, for Codex under **External agents**, and **Sign in with OpenRouter…**, in the OpenRouter provider's form, talk only to `auth.openai.com` and `openrouter.ai`, over HTTPS, with no cookies and no cache. HikariSub makes these requests itself, and the AI component never sees them. The browser returns to HikariSub at `127.0.0.1`, an address on this computer that nothing outside it can reach, and HikariSub stops listening there after that one visit. While a Codex sign-in is still yours, HikariSub renews it with `auth.openai.com` when it has expired and you open **File › Settings › AI**. **Import from ~/.codex (read-only)** reads the sign-in on this computer, sends nothing and never changes `~/.codex`.
- **Keys and sign-ins** are kept in your system's keychain, never in a file. A key goes only to the provider it belongs to, and only over HTTPS. For a custom endpoint it may also go over plain HTTP, but only to this computer or to a Tailscale peer. **Sign out** deletes the sign-in or the key from this computer. A key made by signing in with OpenRouter stays in your OpenRouter keys until you delete it there.
- **The MCP server.** **Let agents outside HikariSub edit through MCP** is off at first. While it's on, HikariSub listens only on this computer: on a local connection only your user can open, and, with **Also listen on http://127.0.0.1**, on that address, only for requests that carry its token. HikariSub sends nothing over the network for it. The agent you connect reads your open files, and what it does with them, such as sending lines to its own AI provider, is up to that agent and its account, not HikariSub. The token and the port are kept in `ai/mcp.json` in your [user folder](/en/docs/automation/user-folder), which only you can read.
- **Prompt caching.** **Use prompt caching**, in the same page's **Privacy** section, is on at first. It asks the provider to keep the start of a conversation for a few minutes, or up to an hour, so the turns that follow cost less. The cache is on the provider, and nothing new is stored on your computer. Turn it off, and HikariSub asks for no caching. OpenAI and Google Gemini still cache on their own, which no request can turn off.
- **The agent.** Nothing goes to a provider until you send a message in the [Agent panel](/en/docs/ai/agent). Then each request in the turn goes to the provider of the thread's model, with your key or sign-in. It carries the thread so far: your messages, the agent's answers, HikariSub's instructions and the list of its tools, and everything the agent's tools returned. What the tools can return:
  - **Your subtitles,** from the active tab and the tabs you attach only: each one's title and its full path on your computer, its lines, styles and Script Info properties, and which lines are selected. Other open tabs aren't listed.
  - **The video and audio** of the active tab: the video's size, frame numbers, times and keyframes, a frame as an image (with all, one or none of the lines drawn on it), and where a line's ink lies on a frame and its colours; the audio's length, sample rate and channels, and its loudness over a stretch of time.
  - **Your settings:** the values of your settings, such as the folders you chose. Your recent files and Projects, and your privacy settings, such as your usage data ID, are kept from the agent. API keys and sign-ins aren't settings, so they never leave this way.
  - **Commands and panels:** their names, whether each is on, and their shortcuts.
  - **Other files:** none for now. The agent can read only files granted to it, and nothing in HikariSub grants it one yet.
- **Skills.** Every request in an Agent panel thread carries the name and description of each [skill](/en/docs/ai/agent#skills), the built-in ones and yours in `ai/skills`, so the provider gets them. A long list is cut short: past about 20,000 characters, the rest are sent by name only. A skill's instructions, and any of its other files, go to the provider only when the agent reads them. From then on they're part of the thread and go with the requests after it, like any tool's answer. Agents connected through MCP and threads on Claude Code get no skills. With **Turn off all AI features** ticked, nothing is read or sent.
- **Claude Code.** A thread on **Claude Code** in the Agent panel runs on your own `claude` program, signed in with your Claude account, not on a provider you added. Its tools are HikariSub's, and they return what they return in any thread, as above. Claude Code's own tools, settings and MCP servers are off, and HikariSub starts it with its non-essential traffic turned off. What Claude Code sends to Anthropic is up to it and your Claude account, not HikariSub.
- **The Claude Agent SDK.** The first time you use a Claude Code thread, HikariSub downloads the Claude Agent SDK, which it uses to talk to `claude`, from the npm registry at `registry.npmjs.org`. The download carries no key, and nothing about you or your subtitles. HikariSub checks it against the hash it was built with, and refuses one that differs. It keeps it in `ai/vendor` in your user folder, and downloads it again only when an AI component update moves to a newer version.
- **Agent versions.** Each time you open **File › Settings**, HikariSub looks for Claude Code and Codex on this computer. For each one it finds, it checks the latest version where that copy was installed from: `registry.npmjs.org` for npm, `formulae.brew.sh` for Homebrew, or `downloads.claude.ai` for Claude's own installer. It asks each source at most once a day and remembers the answer in `ai/agent-versions.json` in your user folder. Each request asks for one program's latest version, with the user agent `HikariSub`, and carries no key and nothing about you or your subtitles. **File › Settings › AI › External agents** shows the result. **Turn off all AI features** stops the checks; there is no separate setting.
- **The judge.** In Auto mode, each change the agent wants to make goes to the provider of the **Judge** model: the change, including any text it would write, and your own messages, never the files it read or what its tools returned.
- **Web search.** With **Let AI search the web** on, the model can search the web, through its provider's own search or the **Search service** you chose. A search sends only the search words, or the address of a page to fetch, never a file. Each Agent panel thread has its own switch, the globe beside **Attach**. With it off, that thread can't search: its requests don't ask for the provider's search, and the search service isn't offered to the model.
  - **What a thread keeps:** when a turn ends, the results a search service returned are dropped from the saved thread. The thread keeps what each search looked for, the pages' addresses, the answer's citations and Google's search suggestions. Results from Anthropic's own search stay in the thread, encrypted as Anthropic sends them, because the answer's citations refer to them.
  - **Showing them fetches nothing:** citations and Google's suggestions are drawn from what the provider sent. A link opens in your browser, and only `http` and `https` links open.

## Plugins

Plugins add to HikariSub's own internet use in two ways: the [plugin manager's](/en/docs/plugins/using-plugins) **Marketplace** downloads the list of plugins, and an installed plugin may connect to the internet for its own work, such as a translation service.

### The Marketplace and plugin updates

The Marketplace's list comes from `https://marketplace.hikarisub.org`. HikariSub downloads the whole list, `index.json`, and its signature, `index.json.minisig`, and works out on this computer what to show and what can be updated. The request never says which plugins you have.

- **When:** at start and once a day while **Check for plugin updates** is on, and whenever you press **Check for updates**, or **Try again** after a failed try. Opening the **Marketplace** downloads the list too, when there is none yet in this run or the last try failed. **Install in HikariSub** on the marketplace website downloads it again, so the plugin is checked against the newest list.
- **What it sends:** two plain downloads, with no query and no cookies, and the user agent `HikariSub/` followed by the version. Nothing is cached, and a redirect isn't followed. The server sees your IP address, as any server does.
- **Search and categories** filter the downloaded list on this computer. What you type is never sent.
- **Install**, **Update to** a new version and **Move to the marketplace** download that one plugin's package from the same site, the same way, only when you press them.
- **Icons and screenshots:** while the plugin manager shows the **Marketplace** view, HikariSub downloads the icons and screenshots of the plugins listed there, from the same site, the same way. It never requests an image from any other site, and the **Installed** view requests none. Each image is checked against the Marketplace's image rules, and kept in memory only, never saved to disk.
- **Automatic updates:** after a check finds a newer version of a marketplace plugin, HikariSub downloads that plugin's package from the same site, the same way, while **Install updates automatically** is ticked for it. The download names only the plugin and version it fetches, as any download of that file would.
- **Turning it off:** clear **Check for plugin updates**, under **Plugin updates** in the plugin manager. It is **on by default**. HikariSub then downloads the list only when you press **Check for updates**, or when you open the Marketplace and it has no list yet.

Nothing else is fetched: links such as a plugin's repository open in your browser only when you click them.

Usage data has no event for the Marketplace either.

### Plugins connecting to the internet

**File › Settings › Updates and privacy › Privacy › Let plugins connect to the internet** is **on by default**. Turn it off, and HikariSub refuses every request a plugin makes through it. It doesn't affect the Marketplace.

Unless it has [full trust](#full-trust-plugins), a plugin can't connect on its own: it asks HikariSub, which makes the request for it. On Linux and Windows, an operating-system sandbox holds it to this: the plugin has no network of its own, and reaches only its own package. Where the sandbox can't apply, for example on a Linux kernel without Landlock or seccomp, HikariSub still makes every request for it, and the plugin's details say *HikariSub keeps it to these permissions, but it isn't sandboxed on this system.*

- **Where:** only the hosts the plugin lists, which the install question and the plugin manager show. A redirect to any other host is refused.
- **How:** only over HTTPS, to the standard port, 443.
- **What it sends:** only what the plugin puts in the request. HikariSub adds its name and version as the user agent, such as `HikariSub/0.1.0`, and never sends cookies.
- **What it keeps:** nothing. Answers aren't cached, and a request is dropped after 30 seconds or when the plugin stops.

Usage data has no event for plugins. It never records that a plugin connected, where, or what it sent. A plugin's own commands aren't in the list of commands it reports. Opening the plugin manager counts as one command, **Plugins…**, like any other.

### Full trust plugins

A plugin marked **Full trust**, in the plugin manager's list or the Marketplace, isn't limited this way. Its install question says it gets full access to your computer, and its button reads **Install with full access**. It runs outside the sandbox, with the same access as HikariSub itself, so it can connect to the internet without asking HikariSub, whatever **Let plugins connect to the internet** says. Install one only from someone you trust.
